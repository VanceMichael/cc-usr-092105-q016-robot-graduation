# 领域约定：机器人毕业能力交接

杭州机器人学校与学校、工厂、海外接收方共建的能力交接后台，为每台机器人保存一条从课堂到职场的完整历史。典藏馆等接收方扫描毕业码，得到的不是一张写着"毕业"的证书，而是岗位所需能力的**当前结论**：现在能做什么、在哪些场景测过、最近换件/升级/换场地后哪些能力还在待复验。

## 扫码三问与结论语义

扫描毕业码时，返回码中每项能力的当前结论 `current_status`：

| 结论 | 含义 | 接收方能否据此派岗 |
| --- | --- | --- |
| `passed` | 最近一次认证通过，且其后没有未完成复验的相关变更 | 可以 |
| `reverifying` | 通过之后发生过硬件/软件/部署变更，尚未重新通过 | 暂不，等待复验结论 |
| `revoked` | 证据范围不覆盖岗位现场等原因，证书已撤销 | 不可以 |

例如样例中 C1 自主路线导览：06-25 在校通过 → 07-05 部署典藏馆后进入场地复验 → 07-22 复验通过 → 08-20 换雷达、09-02 导航升级，**两次变更叠加后当前结论重新回到待复验**。扫码所见即此结论，附带最近证据 E6 与已测场景。

## 核心对象

| 对象 | 内容 |
| --- | --- |
| **机器人身份** `identity` | 入训、出厂、部署、返修、撤销全程不变的 `robot_id`；全部历史沿此身份追加 |
| **硬件配置** `hardware_config` | 按部件槽位记录序列号、安装/更换时间；同槽位列示新旧部件（如雷达 SN-L-2201 → SN-L-2312） |
| **软件版本** `software_versions` | 导航模型、语言包等组件的版本、生效与被替代时间 |
| **课程任务** `course_tasks` | 在校训练科目及完成记录 |
| **实战记录** `field_records` | 学校开放日、场馆夜场、工厂通道、海外远程演示等场景的实地运行记录 |
| **故障处置** `incidents` | 故障现象、处置措施、关联能力与关联返修变更 |
| **能力证据** `evidence` | 考核录像、评分表、演练记录；记录采集时间、上传时间与上传方式（在线/离线） |
| **能力认证** `certifications` | 能力编号、范围、历次决定（通过/撤销）、多方签署与决定当时的配置快照 |
| **毕业赋码** `qr_codes` | 只引用签发时点已通过且未撤销能力的二维码 |
| **部署交接** `receivers` | 接收方、岗位所需能力与最小披露视图 |
| **档案时间线** `timeline` | 沿同一身份、按发生时间追加的事件流 |

## 生命周期

```
入训建档 → 课程/实战（证据可离线采集） → 多方签署认证 → 毕业赋码
        → 部署交接（按岗生成接收方视图）
        → 试岗反馈 ┐
        → 退回返修 ├→ 硬件/软件/部署变更登记 → 受影响能力进入复验 → 沿原能力追加新决定
        → 证书撤销 ┘
```

- **离线补传**：场地无网络时先采集（`upload_mode: offline`），恢复联网后补传。采集时间必须严格早于上传时间，时间线按**采集时间**归位（如 E4 05-18 开放日记录，06-20 才补传）。
- **多人签署**：每个认证决定至少两人签署，且签署人所属机构不少于两方（学校 + 工厂 / 学校 + 接收方）。
- **变更与复验**：硬件更换、模型升级、部署地点变化都登记 `change_events` 并列明受影响能力；最新通过决定之后只要还有变更，当前结论即为 `reverifying`，复验通过沿原能力编号追加新的通过决定（C1 的两条 pass 决定即为例）。
- **沿原身份追加**：试岗反馈必须关联在先部署的接收方；退回返修必须关联故障记录，返修中的部件更换另行登记硬件变更事件；撤销必须先有通过决定、记录原因并多方签署。时间线事件编号唯一、按发生时间排序、`robot_id` 全程一致。
- **当前结论推导**：`revoked`（最新决定是撤销）＞ `reverifying`（最新通过之后存在未被新通过覆盖的变更）＞ `passed`。

## 必须遵守的关系（不变量）

1. **赋码时点**：毕业码只能引用签发时点已有通过决定且未被撤销的能力；签发后能力被撤销不追溯否定签发，但扫码解析反映最新结论。
2. **证据真实**：通过决定必须挂载 ≥1 份档案中真实存在的证据；接收方视图的"已测场景"必须有证据支撑。
3. **多方签署**：每个决定 ≥2 人、≥2 机构。
4. **配置快照一致**：通过决定的 `config_snapshot` 必须是决定当时在装的部件与生效的软件版本。
5. **离线时序**：`captured_at <= uploaded_at`（离线补传为严格小于）。
6. **变更触发复验**：受影响能力在覆盖变更的新通过决定作出前，当前结论只能是待复验。
7. **时间线只追加**：编号唯一、按发生时间单调、身份一致；认证/变更/反馈/返修事件必须能在明细区找到对应记录。
8. **最小披露**：接收方视图的能力清单与岗位需求完全一致；只含当前结论、范围、最近证据、决定日期、已测场景；不得出现部件序列号、签署明细、课程与故障内部记录。
9. **学校侧完整历史**：序列号、签署、课程、故障、历次决定与配置快照保存在完整档案中，不对接收方暴露。

## 样例导读（RG-HZ-0117，导览机器人，纯虚构）

- 五项能力：C1 自主路线导览、C2 多语种讲解（**passed**）、C3 动态避障、C4 工厂通道安全引导（均 **reverifying**）、C5 户外坡道通行（**revoked**，考核坡道与典藏馆接驳坡道参数不符）。
- 毕业码 `GRAD-0117` 06-28 签发，引用 C1–C4；C5 虽于 06-27 通过但未纳入该码，08-25 被撤销后，任何新签发的码都不得再引用。
- 两个接收方视图：典藏馆展厅导览岗需 C1/C2/C3；海外展馆双语接待岗只见 C2。
- 时间线 18 个事件覆盖离线补传（EV02）、急停故障（EV03）、认证与赋码、部署与试岗反馈（EV12）、退回返修（EV14）、换雷达（EV15）、证书撤销（EV17）、导航升级（EV18）。

样例中的名称和编号仅用于说明字段关系，不对应现实中的个人、企业或业务记录。
